做公众号选题 Agent，最容易想到的第一步是把文章发给模型，让它总结、打标签，再生成选题。

这次我先做了更基础的一步：确认文章能被正确读进来。

我的技术博客已经有７篇 Markdown，每篇都有标题、slug、简介、草稿标记和发布日期。第一轮导入没有接数据库，也没有调用模型，而是做了一个只读预览，列出识别到的字段、正文长度、内容指纹，以及处理失败的原因。

## 解析不需要模型

文件头里的字段属于元数据，文件头之后是正文。解析只需要把二者分开，不需要让模型猜作者、标题或发布日期。

Python 标准库没有 YAML 解析器，所以这次用了 PyYAML。标题里可能有冒号，简介可能跨多行，关键词也可能是数组。简单按冒号切字符串，遇到这些内容就容易读错。

还有一个不太显眼的风险：同一个字段出现两次。程序不能悄悄保留最后一个值，否则我们不知道原本想导入哪个标题。因此预览会报告重复字段，并要求修正输入。

## 原文不能被解析过程悄悄改掉

为了以后能重新处理，程序同时保留原始 Markdown 和提取出来的正文。

这一步没有格式化正文，也没有删除代码块。读取文件时还要注意换行：如果读取过程自动把 CRLF 改成 LF，内容指纹也会变。当前实现保留原始换行，以原始文本计算 SHA-256。

这里的指纹只回答「内容有没有变化」，不回答「两篇文章观点是否重复」。一篇文章只改了简介，指纹也会变化；两个作者表达相近观点，也不能因为语义相近就把文章合并。

## 标识与指纹各管一件事

我用来源集合和文章 slug／id 共同定位记录。不同来源可以有相同 slug，同一来源的同一标识如果出现不同内容，则需要判断是不是版本更新。

目前预览只检查同一批次：内容相同就标记重复，内容不同就报告冲突。这还不等于数据库幂等。跨批次重复导入是否会产生重复记录，要等持久化实现后再验证。

另一个需要分清的字段是 `draft: false`。它只能说明文件声明自己不是草稿，不能证明文章现在仍在线发布。预览因此使用「来源声明状态」，不把它说成已核实的发布结果。

## 这一步验证了什么

当前１５项自动化测试通过，覆盖错误日期、缺字段、重复键、正文保留、同批重复与冲突等情况。７篇真实博客文章也全部解析成功，读取前后的文件指纹一致。

这些结果只能证明解析预览的行为，不能证明检索准确，更不能证明 Agent 已经能产出好选题。

下一步才是正文切片：按什么边界拆、如何保护代码块，以及超过模型输入预算时怎么处理。文章先读对、来源先记清，后面检索到的内容才有机会成为可信的证据。
