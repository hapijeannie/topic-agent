# 需求与边界

## 已确认目标

- 创建真正长期使用的公众号选题与写作知识 Agent，而非仅供面试的 Demo。
- 以 L 的企业级 RAG 与 S 的 Agent 执行、Python、行业落地要求为学习主线。
- 保持企业售后 Agent 的执行结构，只替换领域对象：手册对应文章资料，档案对应文章档案，工单对应写作任务。
- 每阶段讲概念并提供经核对的官方资料；每日记录实际进度；里程碑输出博客草稿。
- 在当前独立工作区建立项目，博客作为只读输入与未来发布载体。

## 业务链路

1. 确认账号和可访问知识范围。
2. 输入关键词或想法，必要时补问。
3. 检索历史文章，返回标题、链接或本地来源、相关段落与判断依据。
4. 查询文章发布状态、历史选题及未完成任务。
5. 若值得写且不存在重复任务，生成包含主题、角度、依据和交付要求的任务草稿。
6. 用户确认后创建任务，按指令执行资料收集、起草与审校。
7. 失败时保留状态，支持受控重试和恢复，防止重复业务写入。
8. 验收输出，记录执行步骤、结果、耗时和成本。

分支：已有文章满足需求时返回相关文章；已有任务时返回进度；主题相近但角度不同可建议延伸。没有检索到只能表述为「当前已收录内容中未找到」，不能声称从未写过。

## 素材与存储原则

- 输入包含 Markdown、公众号链接、图片、灵感。当前已有 Markdown 和部分公众号链接，后者尚未提供样本。
- 保留原始输入、解析正文、来源及版本；摘要和标签是派生信息，不替代全文。
- 图片保留原图，OCR 与模型描述分开记录；灵感保留原文，短内容不强制总结。
- 链接获取失败也保存输入和状态，允许重试或补充正文。
- 同文多来源需关联，内容改变需保留版本；相似度不是自动合并的充分依据。
- 区分自己文章、外部参考、草稿、已发布内容。资料、选题、任务是不同对象。
- 业务数据与正文拟用 PostgreSQL，文件拟用对象存储，向量索引拟用 pgvector；均尚未部署。

## 技术方向与待确认项

- 推荐 Python＋LangGraph 承担新项目的 Agent 学习主线，前端可沿用 Next.js 经验。
- 不因旧项目存在而强制采用双后端；具体服务边界、版本及模型供应商待确认。
- 内部工具先跑通，再提供 MCP 接口；Skill 描述方法，运行服务负责权限、状态与执行。
- 多 Agent 在单 Agent 基线建立后做对照实验，不作为第一阶段要求。
- 公众号样本、图片样本、模型预算、部署目标及每周可投入时间待确认，不影响当前文档建项。
