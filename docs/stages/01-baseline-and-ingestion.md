# 第一阶段：理解已有基线，设计素材导入

状态：解析、分块、两表事务保存、本地 POST /documents 和上传页已实现。用户报告合成样例导入符合预期。六项练习的运行检查已通过。上传页只在本地验证。向量化和模型调用尚未开始。

## 目标

以现有７篇文章为首批真实样本，理解原博客的入库与 RAG 链路，确定新项目可追溯、可重复执行的 Markdown 导入方案。该阶段不需要先做完整 Agent 或写作界面。

## 开始前的概念

| 概念 | 含义与项目实例 | 区别及本阶段要求 |
|---|---|---|
| 元数据／Frontmatter | 文件头记录标题、slug、日期等描述信息 | 与正文分开；能解释 draft 是来源声明，不是线上发布证明 |
| 解析 | 将 Markdown 文件拆成结构化字段与正文 | 不等于摘要生成；能识别缺字段或格式不合法 |
| 标识符 | 用来定位同一条记录，如来源项目加 slug | 文件名、内容相似度都不天然是全局唯一标识 |
| 内容指纹／哈希 | 用确定性算法生成内容摘要，检测内容是否改变 | 不判断语义重复；格式变化也可能改变哈希 |
| 去重／版本 | 避免重复记录／记录同一素材的内容变化 | 重复导入与不同来源的同一文章要分别处理 |
| 幂等 | 同一操作重试不会重复产生业务结果 | 同一文章导入两次不应创建两条独立素材 |
| 来源追溯 | 保存内容从哪里来、何时获取和如何处理 | 摘要也必须能找到对应原文版本 |
| 分块／向量 | 将正文分段／将内容编码为数值表示 | 分块保留可读原文，向量用于相似度计算，不代替原文 |

资料入口：

- [CommonMark 代码块规范](https://spec.commonmark.org/0.31.2/#fenced-code-blocks)：已打开核对；注意 Frontmatter 不属于 CommonMark 标准正文语法。
- [PostgreSQL 教程](https://www.postgresql.org/docs/current/tutorial.html)：本会话已打开核对数据库基础入口，实施前再定位所用章节。
- [pgvector 官方仓库](https://github.com/pgvector/pgvector)：本会话已打开核对向量检索入口。

## 分步任务

1. 用户用一篇文章串讲：文件头 → 正文 → 分块 → 向量 → 检索 → 引用。根据实际回答补概念，不根据代码存在推断掌握。
2. 明确素材字段、标识策略、原始与派生内容关系，给出导入结果样例。
3. 先设计不连接数据库、不调用模型的只读解析预览，展示识别字段、内容长度、来源和异常。
4. 阶段方案确认后才实施预览；数据库 schema 及迁移另行确认。
5. Markdown 链路稳定后，用公众号链接和图片样本扩展解析，不预先承诺平台抓取成功率。

## 验收设计

- ７篇真实文件均能识别标题、slug、简介、正文和来源；不改变原文件。
- 缺必填字段、无 Frontmatter、非法日期能明确报告，不静默伪造默认值。
- 代码块和正文完整保留，尤其是代码里的冒号与标题符号。
- 重复输入、正文改变、同 slug 不同来源的预期行为分别定义。
- 预览阶段仅证明解析与判定；只有后续真实存储验证后，才能声称数据库写入幂等。
- 用户能解释为什么保留全文、为什么相似不等于重复、为什么未检索到不等于未写过。

## 历史练习：确定切片规则

场景：文章包含「## 缓存失效」，下面有解释文字和一段代码；代码内部出现字符串「## 这不是标题」。

- P1：按标题切片时，如何避免把代码里的文字误判为新章节？
- P2：如果整段代码比片段长度预算还大，应该报告问题、拆分还是原样放行？说明你的取舍，不要求先写代码。

以上为已进行的练习背景，不要求重新开始切片练习。
